# UX v3 — вознаграждение и тестовые гаранты

Статус: программная реализация в `feature/ux-v3-full-integration`, не завершённый rollout.
Новые правила применяются только к событиям с `EventConfigV3.terms._reward_engine = 1`.
Старые события автоматически не переоцениваются и не мигрируют.

## Финансовая модель

`guarantor_rewards.py` — чистый целочисленный расчёт. Тарифы: `fixed`, `percent`,
`combined`, `percent_minimum`. Общая процентная часть округляется вниз один раз на
событие. Распределение награды: пропорциональные целочисленные квоты и допустимые
наибольшие остатки; при равенстве — стабильный user ID. Минимальная сохранённая прибыль
каждого победителя округляется вверх. Недостаток даже одного nanoTON не заимствуется
из свободного баланса. Невыполнимый план отклоняется.

P считается из фактических исполнений с существующим неттингом позиций: положительная
разница между выплатой и всеми исполненными затратами участника. Matching, приоритет
заявок, self-match protection и прежний сервисный сбор не заменены.

`GUARANTOR_MINIMUM_PROFIT_BPS=2000` — порог 20%. При окончательном согласовании он
фиксируется вместе с редакцией и сторонами: изменение env не переоценивает открытое событие.

После общего согласия — `collecting`; заявки и исполнения возможны, награда не переводится.
Оба исхода проверяются по фактическому банку исполнений. Затем — `active`.
Проверка повторяется **после каждого** нового исполнения; нарушение откатывает всё
размещение, не меняя алгоритм выбора встречных предложений.

Settlement: награда за событие один раз, отдельные проводки `guarantor_reward`,
проверка суммы всех выплат относительно банка, единая транзакция с решением и историей.
Проведены интеграционные проверки rollback и конкурентных повторных решений на SQLite.
PostgreSQL-конкуренция ещё требует отдельной тестовой базы.

Отмена гарантом без победителя, недостаточный фонд к закрытию и пропуск 24 часов:
существующий транзакционный возврат исполненных ставок и неисполненных остатков,
награда 0 и сервисный сбор 0. Пропуск решения учитывается в реальной статистике профиля.

`order_quote` возвращает `requested.guarantor_costs`: точные строки nanoTON,
предварительную выплату, сервисный сбор и награду, `secured_for_both_outcomes`,
`can_place` и причину. Выплата после сборов относится ко **всем исполненным позициям
пользователя по событию**, включая прогнозируемое новое исполнение, не только новой ставке.
При неисполнении/необеспеченности неизвестные суммы — null, а не обещанный доход.
Quick Trade и свой коэффициент используют ответ сервера без клиентской финансовой формулы.

## Модерация

`POST /ux-v3/events/{id}/moderation/publish` принимает `expected_revision`.
Только администратор, только pending public, до торговли. Старая редакция, повторная
публикация или чужой доступ отклоняются. Исправленная версия публикуется без согласия
создателя; исходный автор, история и уведомление сохраняются.

## Автоматические гаранты: отдельное демонстрационное окружение

По умолчанию полностью выключены. Нельзя включать на рабочей базе.
Нужны одновременно:

1. `BETTON_ENVIRONMENT=demo` (или `test`).
2. `BETTON_DEMO_AUTOMATION=true`.
3. Новая отдельная БД, имя которой начинается с `betton-demo-`, `betton_demo_`,
   `betton-test-` или `betton_test_`.
4. Инициализация **пустой** БД командой `python scripts/init_demo_environment.py`
   до первого входа. Создаётся только маркер; существующая непустая БД не принимается.
5. Реальная серверная проверка администратора для установки и включения каждого сценария.

На Windows (PowerShell), только после настройки отдельной тестовой конфигурации:

```powershell
$env:BETTON_ENVIRONMENT = "demo"
$env:BETTON_DEMO_AUTOMATION = "true"
$env:DATABASE_URL = "sqlite:///./betton-demo-ux-v3.sqlite"
python scripts/init_demo_environment.py
```

Это **не** команда запуска Telegram и не выполняет seed. Не переносить сюда рабочую `.env`.
Реальный токен существующего бота и HTTPS настраиваются отдельно после проверки Render,
backup/rollback и характера базы. Не запускать два webhook-обработчика одного бота одновременно.

Администратор после обычной Telegram-авторизации:

- `POST /demo/guarantors/install` — идемпотентно создаёт шесть явно тестовых акторов
  и профили: фикс, процент, сумма, минимум, переговорщик, гибкий. Telegram ID отсутствует,
  начальный баланс 0, фиктивные оценки/отзывы не генерируются.
- Создать обычное событие UX v3 и выбрать нужного тестового гаранта.
- `PUT /demo/guarantors/events/{id}` с JSON `{"scenario":"negotiate","enabled":true}`
  — разрешить конкретный сценарий. `enabled:false` выключает его.
- `GET /demo/guarantors/runs` — состояние, запланированный ответ, последняя ошибка.

Сценарии: `negotiate`, `decline`, `no_response`, `invite_expiry`, `agreement_error`,
`winner_0`, `winner_1`, `cancel`, `timeout`. Последние четыре не ускоряют время и
не рассчитывают событие до реального срока. В `timeout` работает штатная отмена после 24 часов.
Назначение победителя — явно тестовый исход, выбранный администратором, не реальный прогноз.

Worker опрашивает очередь раз в 2 секунды; стратегии задают разные задержки 3–13 секунд.
Гарант не подтверждает условия вместо создателя. Переговорщик сначала задаёт вопрос,
процентный гарант делает уступку, фиксированный принимает только фиксированный тариф.
Все переходы и предложения проходят обычные серверные функции, сохраняют историю и
проверяют актуальную редакцию. Ошибка выключает сценарий, а не имитирует успех.
Перепривязать сценарий к реальному гаранту или legacy-событию нельзя.

## Незавершённая часть общего задания

- Полное разнообразное наполнение демонстрационной БД и повторяемый seed UX v3.
- Подключение отдельной ветки Admin Center к этой же БД.
- Полная визуальная сверка и недостающие Figma-состояния четырёх тарифов.
- Проверка отдельной PostgreSQL-базы и конкурентного timeout/settlement.
- Проверка Render, backup/rollback, rollout в действующем боте и фактический Telegram QA.

Ни один локальный тест или подписанный sandbox-вход не считается проверкой в Telegram.
