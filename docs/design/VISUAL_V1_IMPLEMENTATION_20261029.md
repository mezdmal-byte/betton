## Новое подтверждённое правило времени

В `docs/BETTON_BIBLE.md` зафиксировано уточнение пользователя от 29.10:

- Начало события закрывает приём ставок.
- Без гаранта нет предполагаемого окончания; автор решает после начала, когда захочет.
- С гарантом требуются начало и предполагаемое окончание; окно решения 24 часа сохраняется.

Новая форма отправляет `timing_version: start-v1`. API новых событий без гаранта
возвращает `ends_at: null`. Старый NOT NULL столбец использует начало как внутреннюю
совместимую опору, не как заявленную дату окончания. Старые запросы, hashes повторной
отправки, записи и ограничения по исходному `ends_at` сохранены. Редактор модерации
сохраняет версию протокола и отсутствие окончания.

Проверены потребители `EventConfigV3.ends_at`: workers и дедлайны обеспечения/решения
относятся к событиям с гарантом; решение и отмена частного события без гаранта доступны
после начала. Математика matching, комиссий, ledger и settlement не переписывалась.

## Расхождения, которые нельзя скрывать макетными значениями

1. **Быстрая ставка использует существующий IOC-контракт.** Неисполненный остаток
   возвращается на баланс и не становится предложением. В Figma есть сценарий с
   ожидающим остатком и собственным минимумом. Новый UI честно показывает поведение
   сервера; этот продуктовый разрыв ещё не реализован. `limit`-предложение доступно
   отдельно через свой коэффициент. См. `app/ConnectedQuickTrade.tsx`.
2. Обычная котировка возвращает gross payout без полного net/fee breakdown. Подпись
   «Выплата до сбора» сохраняет смысл; клиент не выдумывает чистую выплату. У гаранта
   используется существующий серверный `guarantor_costs`.
3. В «Моих ставках» отсутствует надёжный признак гаранта для всех элементов API.
   Фильтр «С гарантами» не заменён догадкой по `unlisted`. Сумма потенциальной выплаты
   не названа прибылью. Показатели без данных не заполнены числами из Figma.
4. API гаранта не даёт общего тарифа профиля и доли своевременных решений. UI показывает
   согласование вознаграждения для каждого события и реальные доступные показатели.
   Не введены экзамен, документы или новое предварительное одобрение модератором.
5. Лента сохраняет рабочий фильтр статуса дополнительной строкой; поиск доступен из
   меню; глобальная сумма открытых предложений показана в меню. Это добавления к
   конкретному основному frame, необходимые для сохранения существующих функций.
6. Новые правила времени добавляют начало в частную форму и предполагаемое окончание
   в форму с гарантом, даже если эти поля отсутствуют в старом опорном frame.

## Что остаётся завершить

- Покадровая визуальная приёмка всех состояний переговоров и решения гаранта:
  новый V1 подключён, но браузерный smoke не означает точное совпадение каждого frame.
- Настоящие TON операции, как и прежде, не подключены. RU light настройки, чат,
  модерация и недоступные состояния кошелька перенесены отдельными компонентами.
- Inline-профиль гаранта внутри создания ещё использует `GuarantorDetails`.
- Системные варианты, не охваченные `SystemV1`, остаются прежними. Кнопки без реального
  обработчика не рисуются как рабочие действия.
- Общая приёмка каждого состояния Event/Trade/Portfolio с идентичными Figma fixtures,
  особенно chart, частичное исполнение, неизвестный исход и длинные данные.
- Перенос согласованного поведения ожидающего остатка быстрой ставки и нужных read
  models, затем отдельные финансовые регрессии. Нельзя закрыть это одним изменением текста.
- Проверка в настоящем Telegram WebView, проверка PostgreSQL/concurrency и полный
  контроль локализации. Утверждённый визуальный материал этого прохода — русский light V1.

## Дополнительный проход — 30 октября 2026

Подключены отдельные V1-компоненты без удаления прежних экранов:

- `GuarantorWorkflowV1`: приглашение/отказ, чат/условия/история согласования,
  четыре тарифа для конкретного события, предложение правок, подтверждение редакции,
  согласие участника, выбор нового гаранта, решение/отмена с отдельной проверкой, отзыв.
  API и расчёт денег сохранены. Действия проверяют роль, начало/окончание/дедлайн.
  Редакция фиксируется перед проверкой: её обновление блокирует подтверждение.
  Контроллер блокирует одновременные запросы. Ошибка не очищает введённое обоснование.
- Backend разрешает сохранять новую редакцию условий только создателю. Правки
  гаранта отправляются как явное предложение в чат; UI не объявляет их новой редакцией.
- `ChatV1`: реальные сообщения, ответы, удаление с прежними правами, вложение события
  в общем чате, сохранение черновика/ответа при отказе сервера. В событии добавлен
  preview трёх сообщений с loading/error/empty и отдельным переходом в полный чат.
  Preview не помечает сообщения прочитанными и загружается только после успешного
  чтения события авторизованным пользователем.
- `ModerationV1`: очередь, проверка, редактирование, сравнение, подтверждение публикации,
  отклонение, конфликт редакции. Используются действующие запросы/права/ревизии.
  Время подачи отсутствует в API — вместо выдуманного времени показаны автор и ID.
- `SettingsV1`: тема, язык, безопасность, справка, честные заглушки ещё не опубликованных
  юридических документов. Dark/system и EN/ZH предлагают явный переход в прежний UI;
  предпочтение сохраняется только после подтверждения перехода.
- `WalletV1`: состояния неподключённого кошелька и недоступных пополнения/вывода.
  Нет фиктивного адреса, QR или подмены баланса кошелька внутренним балансом приложения.
  Callback выбора TON/Solana сохранён.
- Словесный знак BetTON экспортирован отдельным native SVG из
  `I819:60880;783:709` (101×32). Это устраняет подтверждённую разницу ширины webfont
  в общей шапке, ленте, фильтрах и создании. Изображения экранов в UI не используются.

Независимый визуальный проход подтвердил основные слоты настроек и недоступного
кошелька; нижний отступ приглашения гаранта исправлен по измерению Figma (4 px).
В очереди модерации статус ограничен шириной содержимого вместо растягивания.
Независимо проверены роли, обновление редакции в финальном подтверждении и
