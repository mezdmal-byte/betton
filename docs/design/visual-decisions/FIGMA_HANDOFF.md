## Правило размеров, прокрутки и полного полотна (согласовано с владельцем 27.10.2026)

**Не масштабируй исходный PNG целиком до высоты телефона.** Рабочая ширина экрана — 390 px, в обычном режиме видимое окно около 844 px (с соблюдением safe area), а не 390×693 px с искусственно уменьшенной типографикой/иконками/нижней навигацией. У Figma-фрейма должны быть нормальные физические размеры элементов; названия, категории, кнопки и коэффициенты не должны становиться крошечными ради 5 карточек на одном скриншоте.

**Две разные модели:**

1. **Бесконечная/потоковая лента (FEED-01):** основной фрейм *видимого экрана* **390×844 px**, нижняя навигация нормальной высоты примерно 64–80 px плюс нужный safe area. Лента скроллится в содержимом, не надо изображать тысячи событий и не надо сжимать карточки до высоты PNG. Для проверки компонентов можно показать отдельный дополнительный длинный sample-список, но это не заменяет корректный видимый экран.
2. **Экран с конечным набором блоков, который длиннее одного окна:** например **EVENT-01 — Событие**, **GUARANTOR-01 — частное пари**, **GUARANTOR-DETAIL — чат/условия/история**, при необходимости **MY-BETS / GUARANTOR-PICK** — делать **ОДИН ПОЛНОРАЗМЕРНЫЙ ДЛИННЫЙ Figma-фрейм (390 px шириной × фактическая высота контента)**. Блоки идут друг за другом сверху вниз; ничего нельзя прятать, обрезать или уменьшать ради высоты 844 px. Пользователь и владелец должны видеть весь экран как одно полотно при прокрутке Figma. Для реального интерфейса, где шапка/CTA/низ sticky, **дополнительно** создавай отдельный **viewport preview 390×844** с демонстрацией поведения закрепления — на самом длинном полотне блоки всё равно видимы без дублирования/перекрытий.
3. **Модальные окна/боковое меню:** основной viewport 390×844, если внутренние пункты длиннее — отдельный длинный кадр контента + пример прокрутки; нижние кнопки и подтверждение не должны перекрывать действия.

**Карточки без изображений:** по умолчанию событие должно быть красиво оформлено **без фотографии**. Фото и баннеры опциональны: не трать время на поиск/генерацию случайных обложек для каждого экрана; **сохраняй смысловые иконки, эмблемы команд, графики и векторные элементы, если они действительно нужны и доступны**, и реализуй отдельное состояние «без логотипов», чтобы несоревновательные события выглядели столь же аккуратно. Нельзя оставлять пустую дырку под отсутствие фото. Отказ от декоративных фотографий НЕ означает упрощения типографики, структуры, графиков или показателей.

**Порядок следующего визуального прохода:** (1) восстановить FEED-01 из слишком уменьшенного 390×693 до 390×844 без сжатия содержимого, сделать актуальными версии full-scroll/QA и проверить читаемость; (2) затем детально переработать **EVENT-01 в длинный полный фрейм** с двумя линиями графика, стаканом/правилами/последними сделками/обсуждением и фиксированными действиями, согласованными с первоначальной генерацией; (3) затем остальные конечные страницы. Не менять стили других экранов без отдельной проверки.

**Не считать масштаб 390×693, скриншот уменьшающий текст или одну только короткую viewport-версию полным решением для страниц с конечной длинной структурой.**

4. Показать скриншоты из Figma / export кадров для проверки, не выдавать оригинальные изображения за готовый результат.
5. Подтвердить, что исходный Figma-проект и прежние страницы не изменились; ни React, ни Python backend, ни production не менялись.
6. Если какие-то элементы технически не удалось сделать редактируемыми — указать прямо, а не замаскировать растровым изображением всей страницы.

## EVENT-01: вкладки именно переключают содержимое, НЕ якорная навигация (решение 27.10.2026)

**Уточнение владельца после просмотра Figma.** Длинное полотно 390×2789 с последовательными разделами нужно для проектной документации / инвентаризации всех элементов. **Это НЕ одна пользовательская страница, на которой все блоки одновременно открыты и до каждого нужно листать.**

В реальном интерфейсе на странице события есть **постоянная верхняя часть** (навигация, компактная шапка события, исходы, основные метрики) и **один активный таб с единственным соответствующим набором блоков под вкладками**:

| Вкладка | Что показывать, а остальное скрывать |
|---|---|
| **График** (по умолчанию) | Две линии исходов, периоды, информативный tooltip, объёмы совершённых сделок по переключателю |
| **Предложения** | Фильтр исходов, по ~3 ценовых уровня на исход, `Коэффициент / Доступно (TON)`, `Показать все`, блок `Последние сделки` |
| **Информация** | `Как определяется результат`, источники, раскрываемые полные правила, `Параметры события`, автор |
| **Обсуждение** | Чат/сообщения и его состояния; не показывать в этом табе длинный график/стакан/правила |

Нажатие на таб **скрывает остальные три** и заменяет контент непосредственно **под одной и той же строкой вкладок**. **Высота страницы меняется по выбранному разделу**. Пользователь прокручивает длинное содержимое только внутри открытого раздела (с привычным основным вертикальным скроллом экрана).

Панель выбора исхода/суммы/ставки — **общая** для всех вкладок, закреплена снизу, не перекрывает контент. В разделе обсуждения предусмотреть отдельный режим ввода, где клавиатура и чат не конфликтуют с панелью ставки. Области нажатия и формат коэффициентов единые.

**Что создать в Figma перед следующим экраном:**
1. Оставить существующий длинный фрейм `EVENT-01 · Событие · Полное полотно` как **документационный overview** всех блоков; не удалять и не пересобирать удачные элементы.
2. На основе уже готовых **редактируемых** компонентов сделать **четыре viewport/scroll-state frames** при 390 px с общими header/outcomes/metrics/sticky CTA: `EVENT-01 / Tab Graph`, `EVENT-01 / Tab Offers`, `EVENT-01 / Tab Info`, `EVENT-01 / Tab Discussion`. Не дублировать лишние блоки внутри каждого.
3. По возможности связать их интерактивными Figma Prototype tab-to-tab переходами; работающий клик в Figma — плюс, но не повод писать React/HTML.
4. На компактной ширине 320 px вкладки не обрезать: сделать горизонтально прокручиваемую строку или равноценное удобное решение.
5. Сравнить не только верхние экраны, но и содержание каждого таба; поправить мелкие ошибки/обрезания, не менять весь дизайн.

**Состояние по итогам ревью:** визуальная концепция EVENT-01 **предварительно принимается как основа** с мелкими геометрическими недочётами. Полное утверждение после демонстрации четырёх состояний вкладок и проверки закреплённой ставки.

**Следующий отдельный визуальный проход после вкладок:** `MY-BETS-01 — Мои ставки`. Сначала обсуждаем действительные проблемы и сверяем `my-bets-v1.png`, а не массово правим одновременно экраны гаранта.

## EVENT-01: ставки и действия ВНЕ четырёх информационных вкладок (дополнение 27.10.2026)

**Критично: табы охватывают ТОЛЬКО четыре информационных раздела** (График, Предложения, Информация, Обсуждение). Они **не заменяют** выбор исхода, размещение ставки и создание собственного предложения. Сохраняются и доступны на всех табах:

- **Общая шапка + исходы + основные показатели** — над вкладками. Выбор исхода может подготовить черновик ставки.
- **`Мои действия`** — ниже содержимого **текущей** вкладки: два различимых сценария `Быстрая ставка` (исполнение доступного встречного предложения/предложений по согласованной P2P-логике) и `Свой коэффициент` (создать новую заявку, которая может ждать совпадения). Не объединять их в одно действие и не удалять при переходе между вкладками.
- **`Предложения` (стакан)** — внутри вкладки: пользователь выбирает конкретный исход/ценовой уровень/доступный объём; выбранное предложение заполняет черновик ставки (исход, фактически доступный коэффициент и лимит доступной суммы). При необходимости показать все предложения, фильтровать по исходу. Не путать предложение с уже исполненной сделкой.
- **Общая нижняя закреплённая панель ставки (ticket)** — вне вкладок, остаётся доступна при переключении; отображает исход, коэффициент, сумму TON, расчёт по действующим формулам с учётом сборов и доступного объёма, явное подтверждение. При отсутствии выбранного исхода — понятное состояние без ложной гарантии коэффициента/выплаты; не создавать фиктивный курс для первой заявки. Для частично исполняемых ордеров отображать остаток и фактические исполнения без обещания фиксированного коэффициента для неисполненной части.
- **Два отдельных сценария на Figma**: (A) выбор конкретной строки стакана → панель ставки с ограничением доступного объёма → подтверждение; (B) выбор исхода → `Свой коэффициент` → форма собственной заявки → ожидание совпадения. Показать и `Быструю ставку` как действие без дополнительной навигации, если предложение доступно.
- **UX:** `Мои действия` логически после открытой вкладки, но закреплённая панель обеспечивает доступ к размещению ставки без необходимости листать вниз; не создавать две независимые формы с противоречивыми коэффициентами. На вкладке `Обсуждение` при фокусе поля ввода учесть клавиатуру, чтобы панель ставки не перекрывала чат.
- **Важное правило визуального handoff:** исходный длинный обзорный фрейм показывает все блоки подряд только для инвентаризации. В рабочем пользовательском варианте **под вкладками только один информационный раздел, затем `Мои действия`, а `ticket` закреплён снизу**. Сделать отдельные интерактивные состояния ставки/выбора предложения в Figma, не писать React.
