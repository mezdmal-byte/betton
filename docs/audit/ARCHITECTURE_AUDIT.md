# Архитектура — заключение по исходникам

## Граф зависимостей и эксплуатация

Граф сохранён в [dependency-graph.json](evidence/dependency-graph.json), генератор — [dependency_graph.py](evidence/dependency_graph.py). Проверены 33 Python-модуля и 190 TS/TSX-модулей, включая tests/stories. Python AST учитывает отложенные импорты; TS regex — относительные import/export, не runtime-generated зависимости.

**A8 / желательное, высокая уверенность:** eager Python циклов не найдено; при включении function-local imports есть группы database/models/money и discovery/guarantor_funding/guarantors/market_service/p2p_ledger/p2p_service/ux_v3_governance. Это не доказательство import crash: отложенные импорты избегают его, но скрывают связи. TS-циклов в извлечённом графе нет. Проверка устранения: доменные DTO и pure helpers не импортируют routes, повторная генерация графа и import smoke test. Полный граф ограничен статически обнаруживаемыми импортами.

**A9 / важный эксплуатационный риск:** [app/database.py:22](https://github.com/mezdmal-byte/betton/blob/1c0f7cb0fa802e3d6a2a77f7873489208a775327/app/database.py#L22) создаёт engine при импорте, config.py создаёт Settings с чтением env; main монтирует frontend по существованию dist в момент импорта. Данные мигрируют в lifespan, не при простом импорте. Бот создаёт Dispatcher и logging configuration при импорте, транспорт Bot ленивый. Следствие: тесты должны задавать env до импорта; отсутствующая сборка при старте останется 503 до рестарта. Приёмка — fresh process с явным test env и готовым dist.

**A10 / важное:** [app/main.py:149–192](https://github.com/mezdmal-byte/betton/blob/1c0f7cb0fa802e3d6a2a77f7873489208a775327/app/main.py#L149-L192) запускает expiry каждые 15 секунд и demo worker каждые 2 секунды в каждой реплике. Ошибки логируются, повтор выполняется следующим циклом; для денежных операций нужны доказанные PG locks. При shutdown asyncio cancellation не останавливает уже выполняющийся to_thread; необходим drain с ограничением времени. Не требуется немедленно вводить очередь: сначала один владелец фонового цикла либо проверенная конкуренция, метрика возраста необработанного срока и alert на повтор ошибки. Приёмка — два процесса, завершение одного посреди операции, повтор без двойной выплаты.

### Контролируемые миграции и восстановление

1. Снять перечень схем/индексов и backup; восстановить в отдельную БД. Зафиксировать baseline существующей версии, не запускать create_all вслепую.
2. Ввести последовательные миграции (например Alembic) отдельной deployment-командой под одним владельцем; приложение только проверяет совместимую версию. Перенести ensure_schema преобразования в однократные миграции с проверкой числа строк.
3. Сначала additive изменения; проверить старый и новый код на расширенной схеме. Backfill небольшими транзакциями с проверкой суммы денег. Destructive cleanup — последующим релизом.
4. Для BIGINT предусмотреть блокировку и lock_timeout. Проверить два одновременных старта. DDL `DATETIME` и `BOOLEAN DEFAULT 0` в ensure_schema требуют проверки старых PostgreSQL схем, где этих колонок ещё нет; текущий тест legacy создаёт часть колонок заранее.
5. Откат приложения сохраняет совместимые расширения схемы; восстановление backup с откатом новых операций требует отдельной процедуры сверки, не обычного автоматического rollback. Реальный restore здесь не выполнен.

Для новых типов событий сначала отделить versioned event policy от транспорта; новый тариф добавлять через чистый reward engine и инварианты округления. Профили/рейтинги развивать с пагинацией. Турниры вводить отдельной сущностью, когда определены правила. Уведомления получают стабильные коды/параметры вместо сохранённого русского текста; outbox нужен при появлении внешней доставки с гарантией повтора. Admin Center — только новые read projections после стабилизации схем, интеграция отложена.

Исходные SHA указаны в AUDIT_PROGRESS.md. Архитектура React + FastAPI + SQLAlchemy пригодна для постепенного развития. Оснований заменять стек или вводить микросервисы в выполненной проверке нет. Нужны локальные границы ответственности и эксплуатационные проверки.

## Карта ответственности

## Окончательный план миграций и восстановления

**Статус:** рекомендации готовы; PostgreSQL, backup/restore и rolling практически не испытаны. Я не могу подтвердить безопасность обновления рабочей базы без этой репетиции. Высокая уверенность в startup DDL по коду, но инцидент потери данных не воспроизведён.

Порядок: baseline фактической схемы → резервная копия и её восстановление → единственный migration runner → расширение telegram_id до BIGINT и таблица идемпотентности → совместимость старого/нового приложения → переключение → удаление старых полей отдельным релизом. `ensure_schema` после перехода должен только проверять поддерживаемую версию, не менять данные. Внедрять миграции раньше таблицы A4, чтобы не создавать ещё один startup ALTER.

На **изолированной тестовой** БД до BIGINT проверить зависимости:

```sql
SELECT conrelid::regclass AS child, pg_get_constraintdef(oid)
FROM pg_constraint WHERE contype = 'f' AND confrelid = 'users'::regclass;
SELECT count(*) FROM users
WHERE telegram_id NOT BETWEEN -2147483648 AND 2147483647;
```

В модели внешние ключи ведут на внутренний users.id. Изменение telegram_id не требует расширять все user_id. Сохранить unique/nullable. Выполнять ALTER под ограниченным lock_timeout в управляемое окно; при конфликте прервать и перенести, не ждать бесконечно. Откат приложения предпочтительно оставляет BIGINT. Сужать нельзя, пока есть большие ID; удаление таких пользователей не является допустимым откатом.

Воспроизводимая репетиция восстановления (команды только для двух новых локальных тестовых баз, роли и пароль через защищённые настройки libpq):

```bash
pg_dump --format=custom --no-owner --no-acl --dbname=betton_test_source --file=audit-backup.dump
createdb betton_test_restored
pg_restore --exit-on-error --single-transaction --no-owner --no-acl --dbname=betton_test_restored audit-backup.dump
```

Перед dump остановить запись **тестового** приложения и сохранить: количество строк/максимальные ID, ограничения/индексы, сумму balance_nano + remaining + pot_nano, результаты reconcile всех P2P-событий, reward и settlement по каждому событию. После restore сравнить те же показатели и sequence nextval, проверить доступ/чтение, завершить заранее подготовленное событие ровно один раз. Старое покрытие журнала incomplete не выдавать за fully_verified. Затем на восстановленной копии выполнить миграцию, запустить старую и новую версии одновременно с fake Telegram transport и повторить сверку. Нельзя считать наличие dump доказательством успешного restore.

Для SQLite сначала backup API SQLite (или штатный .backup) и foreign_key_check на копии; копирование только .db при активном WAL не считать корректным backup. Включение foreign_keys — на каждом новом соединении до транзакций; найденные нарушения исправлять по отдельному плану без удаления финансовой истории.

Rolling: убрать delete_webhook из обычного shutdown; установка/ротация — один управляемый шаг (S1). Проверить старт второго экземпляра, остановку первого и отсутствие повторного DDL; graceful drain фоновой операции, перезапуск после commit до ответа, отсутствие второго начисления. Граница: отмена asyncio-задачи не гарантирует остановку to_thread. Идемпотентность остаётся нужна даже при одном worker.

Для развития сейчас достаточно явной транзакционной границы domain action, стабильных DTO/ошибок и read projections. Новые тарифы добавлять через чистый reward engine с проверкой обоих исходов, округления и индивидуальных 20%. Турниры и новые взаимодействия моделировать после определения правил. Admin Center подключать позже к стабилизированным read-only проекциям; интеграция сейчас не выполнена.
