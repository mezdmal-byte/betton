# Архитектура — промежуточное заключение

Исходные SHA указаны в AUDIT_PROGRESS.md. Архитектура React + FastAPI + SQLAlchemy пригодна для постепенного развития. Оснований заменять стек или вводить микросервисы в выполненной проверке нет. Нужны локальные границы ответственности и эксплуатационные проверки.

## Карта ответственности

React ConnectedApp → connected-экраны → apiRequest/React Query → FastAPI routes → сервисы P2P/governance → SQLAlchemy. Деньги определяет backend. Отдельный чистый guarantor_rewards рассчитывает план; guarantor_funding связывает его с persisted fills; p2p_service проводит деньги; p2p_ledger проверяет журнал.

## Ветки и демонстрация

Demo SHA 82c0e9f добавляет один файл scripts/ux_v3_render_demo.py к проверяемой реализации. Он использует synthetic identities, отдельную SQLite, общий secret cookie и переключение ролей. Это демонстрационный симулятор, даже если открыт из Telegram; проверкой настоящей пользовательской Telegram-авторизации его считать нельзя. Общий доступ выдаёт роли, включая moderator, поэтому он не подходит для рабочих данных. Состояние Render и фактический deployed SHA не подтверждены.

Main d4ed4e7 содержит другую версию bot/main.py: дополнительную demo-кнопку. Не следует переносить утверждения об обработке share payload или /v2 из UX-ветки на main без отдельного теста.

## Admin Center

Проверен код ветки 7b8f8cc: admin_center/store.py:17–23,27–109,336–380. Читает общие users/markets/orders/fills/ledger/settlements и guarantor_cases. SQLite mode=ro и query_only; PostgreSQL ограничен local test/sandbox, роль проверяется на write/owner privileges. Основа совместима с добавленными таблицами, но EventConfigV3/EventRevisionV3 и demo runs не включены в event projection. Нужны новые read-only представления и подписи guarantor_reward, а не слияние всей старой ветки поверх новой реализации. Интеграция не выполнялась.
