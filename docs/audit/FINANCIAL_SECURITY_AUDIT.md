# Финансы и безопасность — заключение по доступной среде

## Подтверждённые диагностические результаты

Пять новых проверок прошли: [код](evidence/test_audit_followup.py), [вывод](evidence/followup-tests.txt). Они не повторяют полный прежний прогон.

- **F1, доказанный важный дефект, высокая уверенность.** При ставках 100/100 TON и награде 5 TON победителю начислены 194 TON: 200 − 1 − 5. История показывает 200 − 1 = 199 TON. Баланс гаранта увеличен на 5 TON, строка истории отсутствует. Журнал проходит reconcile. Искусственный сбой после записи награды полностью откатывает баланс, журнал и settlement.
- **S1, доказанный важный дефект, высокая уверенность.** Настоящие функции webhook из main и UX v3 исполнены изолированно с mock transport: неподписанный update с `/help` достигает dispatcher. В main обработчики `/start`, `/help`, `/demo`; в UX `/start`, `/help`. Потенциальны ответы бота от имени сервиса и нагрузка; отправка сообщения и кража средств не проверялись и не доказаны.
- **S3, доказанный механизм повышения прав при условной конфигурации.** Тестовый пользователь с ID, отличным от admin ID, после смены подписанного username на разрешённый получает `is_admin=true` и проходит `require_admin`. В main username allowlist отсутствует; в UX/demo/admin-ветке присутствует. Рабочую конфигурацию я не могу подтвердить. Это обязательное исправление перед переносом UX v3.

### S1: безопасное внедрение

Использовать отдельный случайный webhook secret, передавать его в `setWebhook(secret_token=...)`, проверять `X-Telegram-Bot-Api-Secret-Token` constant-time до JSON/dispatcher, отсутствие и неверное значение отклонять. Не логировать заголовок. Прокси обязан проверять входящий секрет и использовать согласованный секрет upstream. Убрать delete_webhook из обычного shutdown; установка — одна управляемая deployment-операция. При первом включении безопаснее краткое окно обслуживания: остановить старые обработчики, запустить защищённые, установить webhook с secret, проверить доставку. Не оставлять публичный режим «принимать без секрета» ради rolling. Для следующих ротаций временно принимать два секрета на всех репликах, переключить Telegram, затем удалить старый. Проверки: missing/wrong/correct secret, proxy, старый процесс завершается после нового, повтор update. Ничего из этого на рабочем боте не выполнялось.

### S2: таблицы, миграция и откат

Во всех четырёх проверенных ветках затронут `users.telegram_id` ([app/models.py:44](https://github.com/mezdmal-byte/betton/blob/1c0f7cb0fa802e3d6a2a77f7873489208a775327/app/models.py#L44)). Внешние ключи относятся к внутреннему `users.id`, не к telegram_id; массово менять user_id в orders/fills/settlements не требуется. Перед миграцией подтвердить это pg_catalog на копии фактической БД. Сохранить unique/nullable. Версионная миграция: `ALTER TABLE users ALTER COLUMN telegram_id TYPE BIGINT USING telegram_id::bigint` с ограничением ожидания блокировки и контролируемым окном записи; модель — BigInteger. Сначала backup и проверенное восстановление. Старый код обычно читает BIGINT через Python int, поэтому предпочтителен откат приложения с сохранением расширенного столбца. Обратное сужение разрешено только после проверки всех значений на диапазон INTEGER; удалять реальные большие ID ради отката нельзя.

Тест заполненной копии схемы, сохранения FK/unique и запрета небезопасного сужения подготовлен в `test_postgres_followup.py`; **на PostgreSQL не выполнен**.

### A4/F2/F3: контракты исправления

- Создание: `Idempotency-Key`, серверная таблица `(user_id, operation, key)` unique, canonical body hash, resource_id и результат. Запись ключа, события, приглашения и уведомления — одна транзакция. Повтор того же тела возвращает прежний результат; иное тело с тем же ключом — 409. Не дедуплицировать по одному названию. Pending-клиентский ключ сохранять вместе с черновиком до подтверждения. Внутри одного события повтор invite уже ограничен состоянием `needs_guarantor`; проблема повторного create создаёт отдельные события и приглашения.
- Ставки: серверный unique `(user_id,request_id)` уже есть. Сохранять неизменяемое намерение до отправки и восстанавливать его после reload; добавить чтение результата по request ID с проверкой владельца. Сначала выяснять статус, затем предлагать новую ставку. В IOC изменение acceptedOdds меняет fingerprint даже без reload (ConnectedQuickTrade:198–211); неопределённый первый запрос нельзя считать новой попыткой только из-за новой котировки.
- SQLite: включить foreign_keys на каждом соединении до транзакции, включая create_all; на копии выполнить foreign_key_check и исправить существующие нарушения отдельно. Проверить негативные FK и каскады. Не отключать проверки ради зелёных тестов. Для рабочей конкурентной нагрузки использовать отдельно проверенный PostgreSQL.

### PostgreSQL: честная граница и комплект

Docker отсутствует; postgres/initdb отсутствуют; установка пакетов не завершилась из-за отказа доступа к архивам, namespace предоставляет только UID 0. Рабочая БД не использовалась. `evidence/run_postgres_audit.sh` запускает одноразовый PostgreSQL 16 в Docker на loopback со случайным портом и удаляет только собственный контейнер. Требования: Docker, Python с requirements проекта и psycopg2. Команда: `bash docs/audit/evidence/run_postgres_audit.sh` из checkout. Скрипт проверен bash -n; 12 дополнительных PostgreSQL случаев собраны pytest и пропущены по явному guard — это **не пройденные PostgreSQL-тесты**.

Комплект покрывает settlement/settlement, settlement/cancel, два fill с cancel остатка, расход одного баланса в двух рынках, решение/expiry на границе −1/0/+1 секунда, конкурентное создание, BIGINT. Existing funding suite добавляет два решения и rollback; followup — сбой после reward insert. Проверяются целочисленное сохранение средств, неотрицательные балансы, uniqueness и reconcile. Barrier синхронизирует старт, но не доказывает все interleaving: дополнительно повторять гонки и контролировать SQL lock waits/deadlocks. Добавлены два worker на двух синтетических гарантах и два порядка отключения сценария: до market lock и во время action. Все три случая также skipped. Исправлено имя тестовой БД на betton_test_audit_* и добавлены SQL timeouts; приложение не менялось. Фактический CI файл: `.github/workflows/postgres-p2p-ledger.yml`.

Проверяемый SHA: `1c0f7cb0fa802e3d6a2a77f7873489208a775327`. Дата: 24.10.2026. Это аудит кода и изолированных тестов, не аттестация рабочего окружения.

### PostgreSQL: покрытие и ограничения

12 дополнительных случаев в evidence/test_postgres_followup.py: два расчёта и расчёт/отмена (2), два taker + cancel maker (1), общий баланс в двух рынках (1), решение/expiry −1/0/+1 сек (3), конкурентное создание (1), BIGINT заполненной схемы (1), два worker/два актора (1), отключение до lock/во время action (2). Итого 2+1+1+3+1+1+1+2=12. Все **skipped**, см. postgres-kit-collection.txt. Это отдельные случаи от 12 ранее пропущенных штатных PG-тестов.

Runner также включает tests/test_p2p_journal_postgres.py (unique entry_key, повтор identity, conflict, rollback), p2p/cancel, rewards/funding (четыре тарифа, несколько победителей, обе стороны, hedge, rounding, concurrent final decisions), demo_guarantors и test_audit_followup.py (сбой сразу после reward insert). Прежние SQLite/pure результаты этих suites не являются результатами PG.

Worker-тест проверяет однократность переговорного шага, а не полного payout lifecycle. При приёмке дополнительно повторить два worker на одном обеспеченном winner_0 событии и crash после commit до ответа; сервисная выплата и worker должны быть проверены вместе. Barrier даёт одновременный старт, не все порядки SQL. Два disable-теста задают порядок через Event: действие, уже удерживающее lock, может завершиться до commit отключения; после commit новое действие недопустимо.

Инварианты: сумма balance_nano + remaining + pot_nano до/после неизменна, все суммы неотрицательны, ключи/settlement уникальны, reconcile соответствует fills, при окончательном расчёте банк нулевой и reward один. Проверять SQL lock waits/deadlocks и выполнять гонки в обоих порядках. Не считать skipped/ошибки импорта успешным прогоном.
