# Финансы и безопасность — заключение по доступной среде

## Перепроверка второго этапа

Пять новых проверок прошли: [код](evidence/test_audit_followup.py), [вывод](evidence/followup-tests.txt). Они не повторяют полный прежний прогон.

- **F1, доказанный важный дефект, высокая уверенность.** При ставках 100/100 TON и награде 5 TON победителю начислены 194 TON: 200 − 1 − 5. История показывает 200 − 1 = 199 TON. Баланс гаранта увеличен на 5 TON, строка истории отсутствует. Журнал проходит reconcile. Искусственный сбой после записи награды полностью откатывает баланс, журнал и settlement.
- **S1, доказанный важный дефект, высокая уверенность.** Настоящие функции webhook из main и UX v3 исполнены изолированно с mock transport: неподписанный update с `/help` достигает dispatcher. В main обработчики `/start`, `/help`, `/demo`; в UX `/start`, `/help`. Потенциальны ответы бота от имени сервиса и нагрузка; отправка сообщения и кража средств не проверялись и не доказаны.
- **S3, доказанный механизм повышения прав при условной конфигурации.** Тестовый пользователь с ID, отличным от admin ID, после смены подписанного username на разрешённый получает `is_admin=true` и проходит `require_admin`. В main username allowlist отсутствует; в UX/demo/admin-ветке присутствует. Рабочую конфигурацию я не могу подтвердить. Это обязательное исправление перед переносом UX v3.

### Точная схема F1 без изменения бухгалтерии

`p2p_service.py:647–675` → ledger `guarantor_reward` и net payout → `history.py:71–225` пропускает награду и использует gross SettlementRecord → `api/adapters.ts:420–445` → ActivityScreen и PortfolioScreen. В PortfolioScreen:440–441,604–605 подпись «выплата» также использует gross `payoutTon`, хотя `creditedTon` уже доступен.

Добавить два типа проекции: удержание победителю с отрицательной суммой и доход гаранту с положительной. Стабильные ID производить от ledger entry ID; не создавать новые денежные проводки. Сохранить gross win и fee, добавить reward deduction; не смешивать net win с повторным вычитанием. Fill/loss остаются информационными. Обновить TransactionOut/типы, адаптер, фильтры Activity и три языка. В завершённых ставках показывать «Зачислено» из credited, gross и удержания — раскрываемой детализацией. Приёмка: сумма неинформационных строк равна изменению баланса для победителя, гаранта, автора, нескольких победителей и отмены; старые события не получают выдуманные удержания.

### S1: безопасное внедрение

Использовать отдельный случайный webhook secret, передавать его в `setWebhook(secret_token=...)`, проверять `X-Telegram-Bot-Api-Secret-Token` constant-time до JSON/dispatcher, отсутствие и неверное значение отклонять. Не логировать заголовок. Прокси обязан проверять входящий секрет и использовать согласованный секрет upstream. Убрать delete_webhook из обычного shutdown; установка — одна управляемая deployment-операция. При первом включении безопаснее краткое окно обслуживания: остановить старые обработчики, запустить защищённые, установить webhook с secret, проверить доставку. Не оставлять публичный режим «принимать без секрета» ради rolling. Для следующих ротаций временно принимать два секрета на всех репликах, переключить Telegram, затем удалить старый. Проверки: missing/wrong/correct secret, proxy, старый процесс завершается после нового, повтор update. Ничего из этого на рабочем боте не выполнялось.

### S2: таблицы, миграция и откат

Во всех четырёх проверенных ветках затронут `users.telegram_id` (models.py:44). Внешние ключи относятся к внутреннему `users.id`, не к telegram_id; массово менять user_id в orders/fills/settlements не требуется. Перед миграцией подтвердить это pg_catalog на копии фактической БД. Сохранить unique/nullable. Версионная миграция: `ALTER TABLE users ALTER COLUMN telegram_id TYPE BIGINT USING telegram_id::bigint` с ограничением ожидания блокировки и контролируемым окном записи; модель — BigInteger. Сначала backup и проверенное восстановление. Старый код обычно читает BIGINT через Python int, поэтому предпочтителен откат приложения с сохранением расширенного столбца. Обратное сужение разрешено только после проверки всех значений на диапазон INTEGER; удалять реальные большие ID ради отката нельзя.

Тест заполненной копии схемы, сохранения FK/unique и запрета небезопасного сужения подготовлен в `test_postgres_followup.py`; **на PostgreSQL не выполнен**.

### A4/F2/F3: контракты исправления

- Создание: `Idempotency-Key`, серверная таблица `(user_id, operation, key)` unique, canonical body hash, resource_id и результат. Запись ключа, события, приглашения и уведомления — одна транзакция. Повтор того же тела возвращает прежний результат; иное тело с тем же ключом — 409. Не дедуплицировать по одному названию. Pending-клиентский ключ сохранять вместе с черновиком до подтверждения. Внутри одного события повтор invite уже ограничен состоянием `needs_guarantor`; проблема повторного create создаёт отдельные события и приглашения.
- Ставки: серверный unique `(user_id,request_id)` уже есть. Сохранять неизменяемое намерение до отправки и восстанавливать его после reload; добавить чтение результата по request ID с проверкой владельца. Сначала выяснять статус, затем предлагать новую ставку. В IOC изменение acceptedOdds меняет fingerprint даже без reload (ConnectedQuickTrade:198–211); неопределённый первый запрос нельзя считать новой попыткой только из-за новой котировки.
- SQLite: включить foreign_keys на каждом соединении до транзакции, включая create_all; на копии выполнить foreign_key_check и исправить существующие нарушения отдельно. Проверить негативные FK и каскады. Не отключать проверки ради зелёных тестов. Для рабочей конкурентной нагрузки использовать отдельно проверенный PostgreSQL.

### PostgreSQL: честная граница и комплект

Docker отсутствует; postgres/initdb отсутствуют; установка пакетов не завершилась из-за отказа доступа к архивам, namespace предоставляет только UID 0. Рабочая БД не использовалась. `evidence/run_postgres_audit.sh` запускает одноразовый PostgreSQL 16 в Docker на loopback со случайным портом и удаляет только собственный контейнер. Требования: Docker, Python с requirements проекта и psycopg2. Команда: `bash docs/audit/evidence/run_postgres_audit.sh` из checkout. Скрипт проверен bash -n; 9 новых PostgreSQL случаев собраны pytest и пропущены по явному guard — это **не пройденные PostgreSQL-тесты**.

Комплект покрывает settlement/settlement, settlement/cancel, два fill с cancel остатка, расход одного баланса в двух рынках, решение/expiry на границе −1/0/+1 секунда, конкурентное создание, BIGINT. Existing funding suite добавляет два решения и rollback; followup — сбой после reward insert. Проверяются целочисленное сохранение средств, неотрицательные балансы, uniqueness и reconcile. Barrier синхронизирует старт, но не доказывает все interleaving: дополнительно повторять гонки и контролировать SQL lock waits/deadlocks. Конкуренция двух demo worker и остановка сценария против worker требуют отдельного дополнения. Фактический CI файл: `.github/workflows/postgres-p2p-ledger.yml`.

Проверяемый SHA: `1c0f7cb0fa802e3d6a2a77f7873489208a775327`. Дата: 24.10.2026. Это аудит кода и изолированных тестов, не аттестация рабочего окружения.

## Что подтверждено

- `p2p_service.py:23–112`: Decimal для входа, целые nanoTON, цена в миллионных долях; matching по цене и ID, запрет self-match через candidates, целочисленные лоты через gcd.
- `p2p_service.py:206–275`: блокировка рынка, затем отсортированных пользователей, резерв/сделки/журнал в транзакции; исключения откатываются. Повтор request_id сверяет параметры.
- `money.py:44–64`: условный SQL increment ограничивает баланс и переполнение.
- `p2p_service.py:324–470,605–691`: отмена проверяет банк и суммы исполнений, возвращает остатки и ставки; settlement сверяет сумму выплат с банком. Unique settlement и журнал дополняют блокировки.
- `guarantor_rewards.py:88–207`: фикс, процент, сумма и максимум; единая награда; округление largest remainder; каждому положительному результату сохраняется ceil(прибыль × minimum_keep_bps / 10000). Прибыль считается по всем позициям пользователя в событии, включая встречные ставки.
- `guarantor_funding.py:17–125`: единая согласованная редакция; обе стороны проверяются по реальным fills; после активации сделка, разрушающая обеспечение, отклоняется.
- `ux_v3_governance.py:85–125`: окончательное решение назначенного одобренного гаранта после ends_at и строго до ends_at + 24 часа. Старые admin resolve/cancel ограничены отдельными guard в market_service и p2p_service.
- `demo_guarantors.py:48–76,109–137,207–253`: environment + имя отдельной БД + marker + admin opt-in; Telegram-акторы запрещены; действие и курсор объединены в транзакцию. Изоляция не заменяет контроль конфигурации владельцем сервера.
- `telegram_auth.py:60–126`: HMAC, constant-time compare, отсутствие дубликатов полей, TTL 3600 секунд и допуск будущего времени 30 секунд.

## Проверки и границы

Повторный полный backend-прогон завершился exit 0; в сохранённом выводе 352 точки и 12 `s` (352 passed, 12 skipped). Frontend: 156 passed. Четыре дополнительных диагностических теста: 4 passed, см. `evidence/audit-probes.txt`. Они фиксируют существующие дефекты, а не подтверждают их исправление.

PostgreSQL недоступен: 12 тестов пропущены. SQLite сериализует запись иначе; результаты нельзя переносить на PostgreSQL-конкуренцию. Не проверены реальные данные, резервное восстановление, реальные TON, production secrets, WAF и Telegram-клиент.
