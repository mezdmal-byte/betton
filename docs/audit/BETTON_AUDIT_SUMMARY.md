# BetTON — окончательное заключение независимого аудита

24 октября 2026 года. Аудит закрыт **в пределах доступных исходников и среды**. Это окончательная диагностика и задание на исправления, а не разрешение на выпуск. Рабочий код и финансовые правила не изменены. Ветки main/UX v3/demo, Render, webhook, реальные данные и Admin Center не затронуты.

Проверенные версии: UX v3 `1c0f7cb0fa802e3d6a2a77f7873489208a775327`, demo `82c0e9f2d43ca54952f28c33f9fcf092cfd54261`, main `d4ed4e7d5978300244d0bcde09a2ce10b6ee6b0a`, Admin Center `7b8f8cc7ed7ebf093d63ec48232342e4006e1310`. Сведения разных веток разделены. Состояние фактически развёрнутого сервера и рабочей базы я не могу подтвердить. Полный журнал версий и проверок — [AUDIT_PROGRESS.md](AUDIT_PROGRESS.md).

## A. Общее состояние BetTON

**Разработку можно продолжать на React + FastAPI + SQLAlchemy. Переписывать проект целиком или переходить на микросервисы оснований нет.** Это архитектурная оценка по изученным границам и тестам, не обещание неограниченной нагрузки.

Денежные решения сосредоточены на сервере; расчёт вознаграждения отделён от проведения денег; есть целые nanoTON, журнал, сверка и ограничения повторных операций. Выделение этих частей — хорошая основа. Основной долг: миграции при старте, неявные транзакционные связи HTTP и worker, крупные модули и совместное существование старого/нового интерфейса. Их можно исправлять по частям. [Доказательства и граф](ARCHITECTURE_AUDIT.md).

## B. Безопасность и финансы

**Перенос UX v3 в основной бот сейчас не рекомендован.** Сначала закрыть следующие восемь обязательных пунктов и условия приёмки. Подробные воспроизведения, файлы, последствия, тесты и риск существующим данным — [FINANCIAL_SECURITY_AUDIT.md](FINANCIAL_SECURITY_AUDIT.md).

| ID | Что неисправно | Насколько подтверждено |
|---|---|---|
| S1 | Webhook не проверяет секрет Telegram в main и UX | Изолированные реальные обработчики пропускают неподписанный update в mock dispatcher. Отправка в рабочий бот и кража денег не проверялись |
| S2 | Telegram ID хранится как INTEGER вместо BIGINT | Подтверждён тип PostgreSQL DDL; большой ID выходит из диапазона. Миграция на настоящем PG не исполнена |
| S3 | В UX/demo/admin роль может определяться по username | При тестовом allowlist другой ID после смены username получает admin. Рабочая конфигурация неизвестна. В main такого allowlist нет |
| F1 | История не отражает удержание/доход гаранта | Победителю зачислено 194 TON, история показывает 199; гарант получает 5 без строки. Балансы и журнал согласованы |
| F2 | Ключ повторной ставки хранится только в памяти | Потеря ключа при reload следует из кода. Повторный дебет через настоящий UI не воспроизведён |
| F3 | В SQLite отключена проверка внешних ключей | Диагностический PRAGMA = 0. Наличие нарушенных ссылок в рабочей БД неизвестно |
| A1 | Изменение схемы и backfill выполняются при запуске приложения | Подтверждено кодом; последствия конкурентного старта и старой PG-схемы практически не испытаны |
| A4 | Повтор создания события создаёт второй экземпляр | Воспроизведено последовательным одинаковым POST. PG-конкуренция подготовлена, не выполнена |

Для F1 пример рассчитан так: 200 TON выплата до удержаний − 1 TON сервисный сбор − 5 TON гаранту = 194 TON. История сейчас учитывает только 200 − 1 = 199. Исправлять нужно историю и подписи, **не повторно начислять деньги**. Сбой сразу после записи вознаграждения откатил денежные изменения в SQLite. [Лог пяти дополнительных диагностик](evidence/followup-tests.txt), [их код](evidence/test_audit_followup.py).

Доказанной потери средств или двойной выплаты выполненная проверка не выявила. Это не доказательство отсутствия таких рисков. Условный путь повышения административных прав доказан; его нельзя отложить как косметику. PostgreSQL-конкуренцию я не могу подтвердить.

Четыре тарифа, единое вознаграждение на событие, учёт встречных позиций, распределение округлений, сохранение индивидуального минимума прибыли, обеспечение обоих исходов, отмены и срок 24 часа представлены в коде и прежних SQLite/pure тестах. Автоматические гаранты защищены сочетанием режима среды, имени отдельной базы, marker и административного включения; Telegram-акторы запрещены. Это не заменяет проверку конфигурации выпуска и конкурентной работы. [Разбор механизма](FINANCIAL_SECURITY_AUDIT.md).

## C. Интерфейс и тексты

Подготовлены **C1–C68**: 55 прежних рекомендаций и 13 дополнений по legacy, боту, ошибкам и промежуточным состояниям. Это не 68 равнозначных дефектов: часть — редакторские предложения, C16 уточнён как неиспользуемая строка словаря. Все изменения требуют согласования владельца. [Таблицы с цитатами и источниками](UX_CONTENT_AUDIT.md).

Первыми исправить понимание денег и действий:

- Развести «предложение» и его исполненную часть — «заключённую ставку»; отмена остатка не отменяет уже заключённую ставку.
- Показывать «Зачислено» после всех удержаний, с раскрытием выплаты до удержаний, сбора и вознаграждения гаранта.
- Объяснять: вознаграждение удерживается из прибыли победившей стороны; минимум 20% относится к положительной прибыли пользователя по всему событию, а не к любой сумме ставки.
- Не предлагать слепой повтор после неизвестного результата запроса; сначала исправить F2/A4.
- Исправить «Открыть заново», когда кнопка лишь закрывает WebApp; локализовать реальные ошибки/уведомления, а не только словарь.
- Сократить повторы дохода автора и заглушек кошелька, сохранив ограничения тестовых средств, сроки, окончательность решения и правила возврата.

Структурная сверка показала по 362 ключа legacy и по 321 React для каждого языка без пропусков и несовпадений именованных подстановок; 139 пар переводов создания события заполнены. Но прямые русские строки остаются вне словарей. Это не полноценная локализация всех состояний. [Воспроизводимая проверка](evidence/check_copy_catalogues.cjs), [результат](evidence/copy-catalogues.json).

Вёрстка React на 360/390/430 px и desktop, темы, клавиатура и Telegram Back фактически не проверены. Figma изучена отдельно; совпадение с реализацией не подтверждено. Нельзя выдавать статические UX-замечания за обнаруженные обрезания или наложения. [UX_REVIEW.md](UX_REVIEW.md).

## D. Производительность

Обосновано постепенное разделение экранов, а не замена React. Изолированная диагностическая сборка уменьшила стартовый JS, включая статические зависимости:

| Измерение | До | После | Уменьшение |
|---|---:|---:|---:|
| JS, байты | 706233 | 605852 | 14,21% |
| gzip, байты | 207954 | 180529 | 13,19% |
| Brotli, байты | 166509 | 147703 | 11,29% |

Процент = (до − после) / до × 100. [Измерения](evidence/splitting-result.json) и [метод/план по файлам](FRONTEND_PERFORMANCE_AUDIT.md). Это перенос загрузки части экранов на более поздний момент, не доказанное ускорение телефона и не уменьшение общего функционала. Эксперимент не объединён с приложением.

Оставить вход, ленту, навигацию и критические элементы в старте; создание, портфель, модерацию, профили и помощь загружать по необходимости. Сначала сохранить незавершённые намерения и формы; затем внедрять lazy, ошибки загрузки раздела и предварительную загрузку по намерению. Проверить обновление данных после фонового Telegram и точность инвалидации кеша. Повышать порог предупреждения Vite или добавлять memo везде не требуется.

## E. Готовность к развитию

После обязательных исправлений можно постепенно добавлять функции без большого предварительного рефакторинга. Сейчас нужны управляемая схема БД, явные транзакции, стабильные коды ошибок, идемпотентные операции и корректные read-представления. Новые тарифы должны расширять чистый расчётчик с теми же инвариантами; новые типы событий — явные правила доступа/сроков/решения.

Пагинация истории и каталога, уменьшение N+1 и выделение domain actions полезны по мере расширения. Турниры, очереди, Redis, микросервисы, отдельная аналитическая инфраструктура и интеграция Admin Center сейчас необязательны. Их не следует вводить без требований или измеренной нагрузки. [Архитектурное обоснование](ARCHITECTURE_AUDIT.md).

## G. Последовательность исправлений

| Этап | Задание и зависимость | Трудоёмкость | Условие завершения |
|---|---|---|---|
| 1. Безопасность | S1 + lifecycle webhook A2; S3 стабильные admin ID и proxy. Список ID утверждает владелец | Средняя на каждый блок | Неподписанный запрос не достигает dispatcher; username не повышает права; rolling не снимает webhook |
| 2. Финансы, схема, повторы | F1 — проекции истории, параллельно с подготовкой A1. Затем A1 → S2/F3 → сервер A4 и lookup F2 → клиентские pending intents | F1/S2/A4/F2 — средние; FK hook — небольшая; миграции/restore — крупная совокупность | Сверка истории/баланса, проверенная миграция копии, отсутствие дублей после reload/crash, настоящий PG-прогон без замены skips успехом |
| 3. Подготовка интеграции | После этапов 1–2 собрать кандидат объединения UX v3/main в отдельной ветке и тестовой среде; включить полные PG suites в CI. Исправить финансовые тексты до пользовательской проверки | Крупная совокупная задача | Регрессия, визуальная матрица, Telegram host, restore/rolling выполнены; перенос в рабочий бот — отдельное согласованное действие |
| 4. UX и тексты | Согласовать C1–C68 пакетами: деньги/действия → ошибки/статусы/языки → сокращения. Результаты F1/F2/A4 определяют правильные тексты | Небольшая на экран, средняя по продукту | Нет обещаний неверной выплаты/безопасного повтора; проверены RU/EN/ZH и доступный legacy; сохранены значимые условия |
| 5. React и дальнейшее развитие | После сохранения состояния — lazy boundary, prefetch, возврат из фона, точные запросы; далее пагинация и точечное выделение сервисов | Средняя | Измеримое уменьшение стартовой загрузки без потери форм, плавности и восстановления после ошибок |

Важные улучшения: CI, drain worker, актуализация данных после фона. Желательные: дробление больших модулей, пагинация, локальные UX-сокращения и lazy loading. Необязательные: смена стека, микросервисы, полный редизайн и инфраструктура ещё не определённых турниров. Доказанных критических денежных инцидентов нет; это не снижает обязательность S1/S3 и release gates.

Следующий этап работы — согласованные исправления по этому плану. Начинать аудит заново не требуется. Полные прежние прогоны: 352 backend passed / 12 skipped, 156 frontend passed, 4 первичных и 5 дополнительных диагностик passed. Они не запускались повторно ради финального отчёта; [доказательства](evidence/) сохранены с указанием границ.
