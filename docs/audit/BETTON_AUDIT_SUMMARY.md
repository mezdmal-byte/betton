# BetTON — итог текущего этапа аудита

24 октября 2026 года. Аудит ещё не закрыт полностью: финансовый/архитектурный разбор и измерение сборки выполнены, тексты проверены первым проходом, визуальная часть заблокирована. Зафиксированные SHA — в AUDIT_PROGRESS.md.

Основу проекта можно развивать на React и FastAPI. Полная переделка не обоснована. Главные изменения сейчас нужны в прозрачности денежных операций, безопасности входящего webhook, миграциях и проверках PostgreSQL.

## Самое существенное

1. Вознаграждение гаранта действительно проводится по балансу и журналу, но отсутствует в истории пользователя. Дополнительный тест это воспроизвёл. Исправлять следует отображение/проекцию истории, не формулу выплат.
2. Webhook не проверяет секрет входящего запроса. Изолированный тест показал достижение dispatcher без заголовка; атак на работающий бот не проводилось.
3. Telegram ID объявлен Integer, недостаточный для всех допустимых ID в PostgreSQL. Нужна проверенная миграция в BIGINT.
4. Создание события повторным одинаковым запросом создаёт второй экземпляр. После потери ответа возможны дубликаты.
5. Крупный JS объясняется общей загрузкой экранов. Размер: 706233 байта, gzip 207954, Brotli 166509. Разделение по маршрутам разумнее замены стека.

Подробные доказательства, уверенность и действия: [финансы и безопасность](FINANCIAL_SECURITY_AUDIT.md), [архитектура](ARCHITECTURE_AUDIT.md), [React](FRONTEND_PERFORMANCE_AUDIT.md), [тексты](UX_CONTENT_AUDIT.md), [UX](UX_REVIEW.md).

## Приоритеты

Критические доказанные потери денег/обход финансовых прав: в выполненной проверке не обнаружены. Это не заключение об отсутствии уязвимостей.

Важное: F1/S1/S2, управление админскими правами, миграции при старте, повторные запросы, PostgreSQL-конкуренция, полная ясность удержаний. Желательное: lazy loading, пагинация, точная инвалидация кеша, разбиение крупных модулей, унификация терминов. Необязательное сейчас: микросервисы, смена React/FastAPI, новая сложная инфраструктура, глобальный редизайн.

## Факты, гипотезы, неизвестное

- Факты: полный backend-прогон exit 0 (352 passed/12 skipped по символам сохранённого вывода), frontend 156 passed; production build успешен; дополнительные диагностические тесты 4 passed. Логи и диагностический код находятся в evidence/.
- Подтверждена реализация четырёх тарифов, проверки обоих исходов и сохранения индивидуального минимума прибыли; пройдены существующие SQLite-тесты. Полную конкурентную надёжность это не доказывает.
- Гипотезы: длинные переговорные экраны перегружают пользователя; polling и N+1 станут заметны при росте нагрузки. Нужны измерения и наблюдение.
- Неизвестно: deployed SHA/настройки Render, состояние рабочих данных, restore backup, поведение настоящего Telegram, мобильная вёрстка 360/390/430, полный охват локализации, конкурентные сценарии PostgreSQL. Я не могу это подтвердить в рамках выполненных проверок.

## Точка продолжения

Начать с F1 и PostgreSQL-плана в FINANCIAL_SECURITY_AUDIT.md; затем закончить таблицу текстов по перечню UX_CONTENT_AUDIT.md и провести браузерный маршрут UX_REVIEW.md в доступной безопасной среде. Не начинать аудит заново. Существенные исправления согласовываются отдельно.

Рабочий код, финансовые правила, main, Render, webhook и рабочие БД в этом аудите не изменялись. Созданы только материалы и изолированные диагностические процедуры.
