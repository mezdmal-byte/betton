# Частные пари с гарантом — передача разработчику

## Исходная точка

Рабочая ветка: `feature/guarantor-mvp`, основана на `feature/figma-full-implementation`
(`eb15f09cce84c07606a5ace5be2e3031281253c8`), а не на старом интерфейсе main.
Архив исходного кода: `archive/pre-guarantor-2026-10-08` на том же SHA.

Продовая база, webhook, секреты и настройки Render в этой задаче не менялись.

## Подтверждённая механика

- Частное пари — существующий бинарный P2P, скрытый из ленты и поиска, доступный по ссылке.
- При создании нет ставки, коэффициента или залога. Создатель затем ставит на общих основаниях.
- Для нового частного пари обязателен выбранный гарант с одобренным профилем.
- Минута на отклик, затем пять минут на согласование. Продление на пять минут требует двух разных подтверждений — создателя и гаранта.
- Пока идёт согласование, рынок `closed`: денежные заявки не принимаются. Состояние согласования хранится отдельно в `guarantor_cases`.
- Создатель редактирует вопрос, исходы, критерии, источник и сроки до открытия. Каждая версия сохраняется. Новую версию создатель подтверждает отдельно; гарант принимает именно её.
- Гарант не может быть создателем или делать ставки в этом пари.
- После открытия правила заморожены. Переписка добавляет доказательства, но не меняет правила задним числом.
- Матчинг, частичное исполнение, резервирование и существующие расчёты nanoTON используются без замены формул. Чаевые не менялись.

## Принятые для MVP настройки — нужно утвердить перед запуском

1. **24 часа на возражение** после предложения результата гарантом. Это выбранный при реализации срок, не исходное требование пользователя. До истечения деньги не выплачиваются.
2. «Принимать новые пари» включается на **час**. При открытом видимом приложении heartbeat раз в **30 секунд**; отсутствие heartbeat **90 секунд** скрывает гаранта из доступных. Это доступность для новых запросов, не освобождение от принятых пари.
3. Спор подаёт только владелец исполненной ставки. Решение/возврат по спору — только независимый администратор, который не является создателем, гарантом или участником ставок.
4. Если единственный администратор сам выступает гарантом, он не может разрешить собственный спор: нужен другой независимый администратор. Перед пилотом организовать этот процесс. Не устранять ограничение скрытым обходом.
5. Гарант может передать непроверяемый результат администратору. Пропуск срока результата также передаёт дело администратору.
6. Отзывы — одна оценка 1–5 от участника исполненной ставки после расчёта. Рейтинг — среднее реальных оценок и их количество, не обещание надёжности.
7. Уведомления пока **внутри приложения**, не Telegram push. При закрытом приложении мгновенное уведомление не гарантируется.

## Реализация

`app/services/guarantors.py` — переходы, версии, согласие игрока, обсуждение, спор и вызов существующего settlement.
Все переходы дела блокируют строку рынка тем же способом, что денежные операции: SQLite UPDATE, PostgreSQL FOR UPDATE.
Автоматическая выплата вызывает существующий `p2p_service.settle()` в той же транзакции. Повторный обработчик видит завершённое дело и не платит снова.
Отказ начисления откатывает и выплату, и изменение состояния дела, и уведомления.

`app/guarantor_routes.py` — профиль, одобрение, доступность, дела и уведомления.
`app/models.py` — шесть новых таблиц: профили, дела, сообщения, отзывы, согласия с условиями, уведомления.
Создаются через существующий `ensure_schema()` / `create_all`, без преобразования старых рынков.
Старые частные пари без `GuarantorCase` сохраняют прежний расчёт администратором. Их нельзя автоматически объявлять согласованными с новым гарантом.

React: «Профиль → Гаранты», выбор при создании частного пари, панель условий в карточке, уведомления и предупреждение перед первой ставкой.
Новые экраны сейчас на русском. Полная локализация новых строк на EN/ZH не выполнена.
Удалена подстановка синтетической истории сделок в подключённом экране рынка. Storybook/fixtures остаются инструментами разработки, не данными API.

## Проверки и запуск

```bash
python -m pip install -r requirements.txt
python -m pytest -q tests
npm --prefix frontend ci
npm --prefix frontend test
npm --prefix frontend run build
```

Отдельный браузерный сценарий поднимает собственный localhost-сервер, временную SQLite и использует фиктивный BOT_TOKEN:

```bash
cd frontend
npx playwright install chromium
cd ..
node frontend/tests/guarantor-flow.mjs
```

Если Chromium уже установлен, путь передаётся через `BETTON_CHROMIUM_PATH`.
`BETTON_QA_OUTPUT` задаёт папку скриншотов. Скрипт не подключается к продовой БД.
Точные результаты последнего прогона указываются в PR, не подразумеваются самим наличием тестов.

Проверено 2026-10-08 в этой ветке:

- `python -m pytest -q tests --disable-warnings`: **272 passed, 12 skipped** на изолированной SQLite.
- `npm --prefix frontend test`: **103 passed**, 16 файлов.
- `npm --prefix frontend run build`: успешно; остаётся предупреждение Vite о JS-бандле больше 500 kB.
- Настоящий headless Chromium + отдельный FastAPI: приглашение → ознакомление → правка условий → подтверждение версии создателем и гарантом → открытие → согласие игрока. Скриншоты на 390/320/1280 px, без горизонтального переполнения на проверенных мобильных ширинах.
- Серверные тесты также проверяют спор/возврат, независимый административный расчёт, повторный и параллельный обработчик выплаты, отзыв, доступ участника без повторного токена, просрочку, отзыв допуска и откат при несогласованном банке.
- При HTTP 409 автоматической выплаты транзакция откатывается; отдельная запись передаёт дело администратору, чтобы истёкшее предложение не оставалось без доступного действия.
- Отдельное визуальное ревью: три найденных замечания по срокам, подтверждениям и приоритету кнопок исправлены и подтверждены. Это не ревью всех экранов приложения.
- PostgreSQL и живой Telegram-клиент не проверены. Истечение реального 24-часового интервала не ожидалось: серверные тесты переводят дедлайн в прошлое.

## Ручная приёмка

1. Независимый админ и минимум три аккаунта: создатель, гарант, второй игрок.
2. Гарант заполняет профиль. Админ одобряет. Гарант включает доступность и остаётся в приложении.
3. Создатель создаёт частное пари: вопрос, два исхода, критерии, подтверждение, сроки, гарант. Баланс не меняется.
4. Гарант получает уведомление и откликается за минуту. Отдельно проверить пропущенное приглашение и повторный выбор.
5. Гарант пишет уточнение. Создатель меняет условия, подтверждает новую версию. Старая версия не принимается. Гарант принимает новую.
6. Каждый игрок читает условия и подтверждает выбор гаранта. После этого размещает заявки. Гаранту ставки запрещены сервером.
7. После остановки приёма гарант выбирает исход, прикладывает обоснование и подтверждает. До конца окна возражений выплаты нет.
8. Без спора после срока — автоматическая выплата. С возражением — деньги остаются заблокированы до независимого решения админа или отмены.
9. Проверить отсутствие двойных выплат, историю ставок, однократный отзыв и счётчик реальных отзывов.
10. Отдельно проверить обычное публичное пари и старое частное пари.

## До передачи Никите / до реальных средств

Это демонстрационный MVP, не сертификация безопасности и не готовность к реальным TON.

- Перед любым деплоем: резервная копия действующей БД и проверка восстановления. Git-архив не заменяет её.
- Проверить PostgreSQL отдельным прогоном: SQLite не доказывает корректность PostgreSQL-блокировок.
- Проверить Telegram Mini App на реальных iOS/Android: initData, возврат по ссылке, кнопка назад, фон/возврат, истечение авторизации.
- Решить, какая ветка и какой Render-сервис будут каноническими. Не сливать в старый main вслепую; Figma-сервис и основной бот сейчас могут использовать разные ветки.
- Перед нагрузкой: пагинация обсуждений/списков, лимиты создания приглашений, доставка уведомлений вне приложения, надёжный отдельный обработчик дедлайнов, мониторинг зависших выплат. Текущий цикл работает только пока процесс приложения запущен.
- Проверить роль администратора по стабильным Telegram ID. В исходном проекте также поддерживается допуск по username; это требует отдельного решения, поскольку имя можно изменить.
- Защититься от накрутки отзывов/нескольких аккаунтов и от сговора. Рейтинг и предупреждение эти риски не устраняют.
- Не удалять legacy LMSR до проверки отсутствия старых позиций и обязательств. Новый пользовательский путь остаётся P2P.
- Перед реальными деньгами: независимая проверка денежных инвариантов, миграций, авторизации, разрешения споров и юридической модели. TON Connect сам по себе этого не решает.
