## S1 — webhook

Изменены `app/webhook_security.py`, `app/main.py`, `app/config.py`, `.env.example`; добавлен `tests/test_webhook_security.py` в обеих рабочих ветках.

Секрет отделён от BOT_TOKEN; секретные поля исключены из repr настроек. Проверяются формат и единственный заголовок, сравнение выполняется через `hmac.compare_digest`. Неверный/отсутствующий секрет → 403 до JSON parsing/dispatch; отсутствующая конфигурация → 503. Forwarded/IP-заголовки не дают обхода. При проксировании нужен отдельный секрет upstream: входной секрет не пересылается автоматически. TLS завершается на доверенном reverse proxy, который должен сохранять единственный заголовок и не логировать его.

Обычный startup не регистрирует webhook; shutdown не удаляет его. UX сохраняет получение username бота. Регистрация — явная команда `python -m app.webhook_security register`. Изменение menu button больше не побочный эффект старта сервера; его обновление — отдельная операция запуска бота, если требуется смена URL.

Тесты: верный/неверный/отсутствующий секрет, некорректный формат, дубликат заголовка, overlap и отзыв предыдущего секрета, повтор authenticated update, отдельный upstream secret, параметры регистрации без удаления pending updates, shutdown старой реплики. Повтор Telegram update принимается: S1 не добавляет небезопасную дедупликацию в памяти и не заменяет идемпотентность денежных команд.

### Переход без рассинхронизации (только после отдельного согласования)

1. В защищённом окружении создать 32 случайных байта через `secrets.token_urlsafe(32)`; сохранить результат только в secret manager. Не вводить секрет в аргументы shell/URL/логи. Проверить HTTPS base URL и отсутствие логирования заголовка.
2. На работающем старом коде сначала убрать автоматическую регистрацию/удаление webhook отдельным подготовительным релизом либо согласовать короткое окно обслуживания. Дождаться остановки всех старых реплик: иначе они могут перезаписать настройки Telegram. Нельзя обещать бесшовный переход старого небезопасного lifecycle одним rolling deploy.
3. Задать секрет новой версии. Явно зарегистрировать его командой выше с `drop_pending_updates=False`, затем переключить весь трафик на проверяющую версию. Пока новая версия не готова, Telegram может повторять доставку; не удалять очередь. При blue/green старая версия временно остаётся с прежней уязвимостью до полного переключения. Сократить это окно, не оставлять смешанные реплики.
4. Проверить доставку настоящей безвредной команды владельца, отсутствие 403 на Telegram и отклонение неавторизованного запроса в staging. Не выполнять диагностические денежные операции в production.
5. Для ротации: сначала все реплики принимают новый current и старый previous; после остановки старых реплик один раз зарегистрировать новый current; проверить доставку и удалить previous на всех репликах. Откат допустим только на версию с проверкой секрета и совпадающей конфигурацией.

Контракт Telegram: https://core.telegram.org/bots/api#setwebhook (secret_token; X-Telegram-Bot-Api-Secret-Token). Проект требует 32–256 символов разрешённого алфавита, что строже минимальной длины Telegram.

## F1 — история без повторных начислений

Исправлены read-only проекции `app/services/history.py`, `app/services/market_service.py` и контракт `SettlementOut`. Выигрыш в истории теперь равен фактическому net payout из ledger; для legacy без ledger используется сохранённый `credited`. Сервисный сбор и удержание гаранту — поясняющие строки с `amount_nano=0`, отрицательным `display_nano` и `informational=true`: они уже включены в net payout. Доход гаранта — положительная операция из `guarantor_reward`. Поэтому суммировать для сверки надо `amount_nano`, не `display_nano`. Это уточнение существующего API-контракта необходимо учесть любому внешнему потребителю истории.

React Portfolio, адаптеры/types, RU/EN/ZH и legacy account/miniapp показывают net credit, отдельные удержания и пояснение, что удержания уже учтены. Settlement API отдаёт размер удержания гаранту из бухгалтерских записей. Frontend не рассчитывает распределение вознаграждения. Matching, reserve, settlement и начисления не изменены; исправление истории не требует переигрывать старые расчёты и не создаёт новых денежных записей.

Проверено: сценарий 200−1−5=194, доход гаранта 5, сверка истории с изменением баланса каждого участника; все четыре тарифа × оба исхода, несколько победителей и несколько исполнений, частичные исполнения и возврат остатка. Существующие тесты отмен, противоположных позиций и отката вошли в общую регрессию. Read-only проверка подтверждает, что чтение не увеличивает число записей ledger.

Backend после F1: **366 passed, 12 skipped** (PostgreSQL), 6 предупреждений deprecation. До F1 после S1/S3: 365 passed, 12 skipped. Отдельный frontend-тест проверяет сохранение gross/service fee/reward/net из API без перерасчёта. Визуальное тестирование на устройствах не выполнено.

Уточнение S3: `ADMIN_TELEGRAM_ID` также выбирает существующий счёт платформы для сервисного сбора. Его нельзя убирать только потому, что добавлен `ADMIN_TELEGRAM_IDS`; список дополнительных администраторов не меняет получателя денег. ## F3 — SQLite foreign keys

`app/database.py`: listener каждого нового SQLite-соединения включает и проверяет `PRAGMA foreign_keys=ON`. Перед изменением схемы `ensure_schema` выполняется read-only `foreign_key_check`; при нарушениях запуск останавливается, записи не удаляются/исправляются автоматически. Проверка работает только для реально объявленных FK; недостающие ограничения старой схемы должны быть отдельно обработаны версионными миграциями A1.

`tests/test_sqlite_foreign_keys.py`: новый пул после dispose, допустимая связь, отклонение несуществующей ссылки и удаления родителя; изолированная старая база с orphan-записью отклоняется и сохраняет запись без изменения. Рабочие данные не читались. Перед развёртыванием нужен preflight на копии действующей SQLite-базы; заранее нельзя обещать отсутствие orphan-записей.

Общая регрессия после F3 и дополнительного отзыва S3: **369 passed, 12 skipped**, 6 предупреждений. Тесты не потребовали ослабления FK или удаления финансовых записей. A1 остаётся открытым: startup пока вызывает ensure_schema.

### Порядок применения (НЕ выполнен на production)

1. Остановить записи и подготовить проверяемую резервную копию. PostgreSQL: pg_dump custom format и pg_restore в отдельную тестовую базу; SQLite: online backup API либо копирование после остановки всех писателей, с учётом WAL. Проверить числа записей, FK, nano-суммы и ledger.reconcile на восстановленной копии.
2. На копии выполнить `python -m app.migrations upgrade`, затем `python -m app.migrations check`; проверить старые события/пользователей и денежные инварианты. Для legacy money сначала согласованная money_migrate на копии. Версию вручную не stamp-ить вместо проверки.
3. После отдельного согласования один maintenance job выполняет upgrade действующей базы; перед запуском новых реплик check должен пройти. Другой мигратор блокируется; приложение само не мигрирует.
4. Ошибка внутри upgrade откатывает транзакцию. После успешной миграции предпочтителен rollback к совместимому приложению при сохранении расширенного BIGINT. Не сужать тип, если есть ID вне int32. Откат baseline-преобразований — восстановление проверенной копии при остановленных записях; учитывать новые записи после backup. Автоматический destructive downgrade не предусмотрен.
